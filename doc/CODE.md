## 1. Architecture and design

localSIEM is a lightweight SIEM for **one Linux server**, installed on that same server (one localSIEM per server). It reads the logs of the services of the server (only of its own server: there is no remote input), stores them in a searchable database, decides what still needs a human and sends that to the PYMEHackers SOC (`soc.pymehackers.com`). The analyst of the SOC investigates the alerts with the search tool of localSIEM. Version 2.2.0 (`cVersion` in [backend/core/config.py](../backend/core/config.py)).

### The guiding principle: «no action taken, to the SOC»

Everything that reaches the SOC is something nobody has resolved yet:

| Situation | `action` | To the SOC? |
|---|---|---|
| ModSecurity blocked it in phases 1-2 (the application never received the request) | `blocked` | No: stored in localSIEM, searchable, and counted in the `context` of the next alert of that IP |
| ModSecurity blocked it in phases 3-4 (the application had already run it) | `none` | Yes |
| Rule matches with the engine in `DetectionOnly` | `none` | Yes |
| Rule matches below the anomaly threshold | `none` | Yes (severity `low`, configurable) |
| Signals of the module rules (brute force, web shell...) and health signals | `none` | Yes |

Every match without an action taken goes to the SOC whatever its score. Sensitive data (passwords, cookies, `Authorization`, tokens, request bodies) is masked before anything is stored and never travels to the SOC.

### Two processes, one writer

| Service | Process | Role |
|---|---|---|
| `localsiem` | [backend/collector.py](../backend/collector.py) | Loads the modules, reads their sources, parses, correlates, applies the rules, stores, groups, sends to the SOC and sends the heartbeat. **The only process that writes the events database.** |
| `localsiem-web` | [backend/server.py](../backend/server.py) | FastAPI + uvicorn serving HTTPS directly on its own port, always 10443 (`config.cWebPort`). Reads the events database; writes only its own database (accounts, sessions, search audit) and `settings.json`. |

The web uses the Unix socket `/opt/localsiem/run/collector.sock` (JSON lines) only to give the collector commands: `reload` after the administrator changes a setting or a module, or presses Reconfigure, so the collector applies it at once; `doctor`; `restart` after a module is installed, updated or uninstalled from the web; and the retry and requeue of the SOC queue. The collector stays the only writer of the events database. If the web stops, collecting and alerting go on. The live view polls the database by the last event id.

### Core and modules

The core knows nothing about Apache and **imports no module by name**. Storage, search, rules engine, grouping, SOC queue, heartbeat and health are generic ([backend/core/](../backend/core/)). Each service of the server is a module: a folder with a `module.json`, the code of a subclass of `Module` ([backend/core/module.py](../backend/core/module.py)) that provides discovery, inputs, framing and parsing, correlation, the decision about the action taken, YAML rules, enrichment, a doctor, its requirements (`mRequirements`), health signals and its web and root hooks, and `locales/<language>.json` with its texts.

The registry ([backend/core/registry.py](../backend/core/registry.py)) finds the modules in one place only; the core has no module of its own:

| Place | Modules | Imported as |
|---|---|---|
| `cModulesPath` = `/opt/localsiem/modules/<name>/` (`LOCALSIEM_MODULES_PATH` in development copies) | Installed, updated and uninstalled only by the web (Modules › Installable, and Update and Uninstall in Modules › Installed, [backend/core/catalog.py](../backend/core/catalog.py)) from the repository `localSIEM-modules` (GitHub), where the folder of each module is `mod-<name>/`; never by the installer of localSIEM; today `apache2` (access.log, error.log and the ModSecurity audit log; folder `mod-apache2/`), documented in that project | the namespace package `localsiem_modules.<name>.<file>`: no `__init__.py`, the module imports its own files relatively and the core as `backend.core.*` |

`module.json` holds: `id` (the folder name, without `mod-` in the repository: `[a-z][a-z0-9_]{1,31}`), `version`, `core` (the lowest localSIEM version it needs; a newer one stops it from loading), `entry` (`"file:Class"`), `default_enabled`, `read_paths` (folders that `manage.py setup-modules` and the installer let `localsiem` read through ACLs), `setup_option` (the option of `manage.py setup-modules` that applies its requirements to its service, such as `--configure-apache`) and `settings`: a list of `{key, type, default, ...}` with type `boolean`, `integer` (`min`, `max`), `string` (`max_length`), `path` (absolute), `choice` (`choices`) or `records` (`fields`, `max_items`; a list of small records, such as the sources added by hand). The web builds the settings form from that list and the registry validates what the administrator saves (`fValidateSettings`).

The settings of a module live in `settings.json` under `modules.<name>`, over the defaults of its `module.json` (`fModuleSettings`, `Module.mModuleSettings`); the defaults of `config.dDefaults` no longer contain any module. `modules.<name>.enabled` turns a module on and off without restarting anything: the collector stops discovering and reading its sources, its doctor and its health checks. A module that fails to load (invalid `module.json`, newer `core`, import error, exception in `mStart`) is reported in the collector log, in `collector.status.module_errors`, in the doctor and in the web, and the others go on.

**Requirements.** Installing a module never installs the software it watches. `Module.mRequirements()` returns what the server must have before the module can be turned on, as checks with the format of `mDoctor` (`{id, status: ok|error, title, detail, fix}`); they are met when no check is an error, and `[]` (the default) means no requirements: the module behaves as before. It is called without storage and may read the configuration of the service every time, so it is never called per request nor per cycle: `fCheckRequirements` ([backend/core/registry.py](../backend/core/registry.py)) runs it (an exception counts as not met) and the result is kept, by the collector when it starts and reloads (state `<name>.requirements`) and by the web (`WebContext.dRequirements`) at the first installation, when a module is turned on and with Reconfigure; the web uses the newest of both. On the first installation from the web (no previous copy) the module is created from the installed copy, never from the downloaded repository, and if a requirement is missing and the administrator never saved `modules.<name>.enabled`, `false` is saved there; an update or a reinstallation never changes it. While one is missing the module cannot be turned on (422 `requirements_missing`, locked switch); Reconfigure checks them again and, when they are met, unlocks the switch and shows the root command, but never turns the module on. Nothing turns a module off by itself: a module that is on and no longer meets them stays on, and its doctor and its health report it.

### Two dashboards

Administrators always work in `/admin/dashboard/` (tabs `overview`, `search`, `live`, `alerts`, `modules`, `users`, `soc`, `channels` (sections `general/`, the default, and `telegram/`), `settings`, `audit`, `logins`, `account`; `modules` has two sections, `installed/` (the default: the installed modules, one row each) and `installable/` (the modules of the repository that are not installed yet), and the page of one module is `/admin/dashboard/modules/installed/<name>/`); analysts work in `/user/dashboard/` (`overview`, `search`, `live`, `alerts`, `modules` read-only and without sections, `account`). The default tab of both is `overview`; `/` and the sign-in take each user to the overview of their dashboard. A URL of the other dashboard is redirected to the same tab of one's own (an administrator asking `/user/dashboard/search/?q=...` goes to `/admin/dashboard/search/?q=...`; an analyst asking `/admin/dashboard/users/` goes to `/user/dashboard/overview/`), both by the server ([backend/web/app.py](../backend/web/app.py)) and by the router of the page ([frontend/assets/app.js](../frontend/assets/app.js)). The sidebar has no headings nor user data: the logo, a line, the tabs (a line between each group) and, at the bottom, a line and «Sign out». The sources, the doctor and the rules no longer have a tab of their own: they are part of the page of each module.

### Records, events and groups

- A **record** is one line or one audit entry as read, already masked. It is stored at once together with the position of its file, in the same transaction: after a crash both are there or neither, so no line is lost or repeated.
- An **event** is one request: the records that the correlator of the module joins. In the Apache module, the records with the same `UNIQUE_ID` joined after the correlation window (5 s); without `UNIQUE_ID` (the access formats Apache writes by default) the access line is paired with the records of its request by client IP, method, URI, status and time (±2 s) and the event is marked as weakly correlated. Records that wait for their window survive a restart (`event_id IS NULL`).
- A **group** is one SOC alert: detections with the same module, vhost, IP, category and severity inside a window (10 minutes). Critical groups leave at once; the others wait a 60-second buffer to gather the burst.

### Storage

SQLite in WAL mode (`/opt/localsiem/db/localsiem.db`, mode 600, `auto_vacuum = INCREMENTAL`), behind the interface of [backend/core/storage.py](../backend/core/storage.py) so a PostgreSQL implementation can be added for a future central mode. Typed and indexed columns for the usual fields; a contentless FTS5 table (`contentless_delete=1`) indexes the masked text, URL-decoded too, so `"union select"` also finds `id=1%27%20UNION%20SELECT`. For audit records only a reduced text (request line, host, user agent, rule ids, messages and data) is indexed. Every query uses parameters: the search tree is compiled into SQL with placeholders in `fCompileQuery`, never by concatenating user text. The overview and the modules page read per-module counts of the last 24 hours (`mModuleCounts`) and alert counts (`mAlertCounts`) with the same time limit as the searches.

Times are stored in UTC in the native storage format `2026-10-29@13-59-59.723` (fixed width, sorts as text) and shown in the display format `2026/10/29@13:59:59.723` ([backend/core/timeutil.py](../backend/core/timeutil.py)). Apache writes local times; the Apache module converts them to UTC (access and audit carry their offset; error.log uses the time zone of the server). Whatever is written as a record also uses the storage format: the database, the logs, the credentials file, the exported CSV and JSON files and the alerts sent to the SOC.

Retention: by days (90) and by maximum size (the lesser of 15 % of the disk and 10 GB). The oldest events go first in short batches; alerts and the SOC queue are kept longer (365 days). With little free disk the bulky detail (audit headers and bodies) is no longer stored; with almost none, only events that take part in an alert. localSIEM never fills the disk.

### Design decisions worth knowing

- **The installer of localSIEM installs the core only.** It runs straight from GitHub (`curl -fsSL .../deploy/install-update-reinstall-debian.sh | bash -s -- ACTION options`): when it is not inside a complete copy (piped, `BASH_SOURCE` is `main`) it downloads the archive of the branch or tag of `--ref` (or `--source-url`). Everything is inside functions and `fMain` runs on the last line, so a download cut halfway runs nothing; no command reads stdin (it is the script itself): commands get `< /dev/null` and questions read `/dev/tty`. It installs the missing packages (`dpkg-query` / `apk info -e`) and keeps the modules already installed. It refuses the setup options of the modules (`--configure-*`: they go to `manage.py setup-modules`) and `--modules-from`. It always needs exactly one action (`vAction`; without one it stops and lists them): `--install` stops when `fIsInstalled` finds any trace of localSIEM (also of an installation that failed halfway), and `--update` and `--reinstall` when it finds none. `--update` keeps everything (data, accounts, settings, modules, the options of `install.env`). `--reinstall` asks first (`fConfirmRemoval`), downloads the new copy and checks its options, and only then deletes everything as `--uninstall` does (`fRemoveInstallation`, which keeps the copy just downloaded) and installs from zero; run from the installed copy it downloads localSIEM, since that copy goes too. The action and `--yes` are not passed to `configure.py`. `--uninstall` (alone or with `--yes`; `fUninstall`, before anything is downloaded or installed) removes everything localSIEM put on the server: services, `/opt/localsiem`, the user and the group, the ACLs of the read paths (`manage.py read-paths`, plus `/var/log/apache2`), the `localsiem.conf` of Apache (configtest, then reload; `localsiem_access.log*` stays: localSIEM never changes nor deletes a log), logrotate, the Let's Encrypt hook and its blocks of the credentials file; it asks on `/dev/tty` unless `--yes`.
- **Downloads from GitHub never use a cache.** `raw.githubusercontent.com` serves a file up to 5 minutes old after a push (`Cache-Control: max-age=300`; neither a query string nor a `Cache-Control: no-cache` request skips it), and the archive of a branch could be old too. So the documented command reads the installer through the API (`api.github.com/repos/.../contents/...`, which is not cached), and both the installers (`fResolveRef` of the installers) and the web, for the modules (`fResolveRef` of `catalog.py`), ask the API for the commit of the branch and download the archive of that commit, which never changes; every download sends `Cache-Control: no-cache`. Without a token the API allows 60 requests per hour from each IP address; without an answer they download the archive of the branch (the installer warns).
- **Channels are a copy for people, not a second SOC.** The collector queues every alert for the SOC (persistent queue; without a SOC it keeps it as not sent) and also hands it to `ChannelSender` ([backend/core/channels.py](../backend/core/channels.py)), which sends the ones of `channels.min_severity` or above through each channel that is on and set up (Telegram: `sendMessage`, plain text, in `channels.language`). Its lists live in memory (200 messages per channel at most), one message per second, with retries on 429 (`retry_after`) and on network errors; a 400, 401, 403 or 404 drops the message at once. A restart loses what was waiting; the SOC still gets every alert. The token of the bot is a secret like the SOC token: `config/telegram-bot-token` (mode 600), never shown whole nor logged, and the URL that carries it is never written.
- **The SOC is optional.** `fSocConfigured` ([backend/core/soc.py](../backend/core/soc.py)): a URL, a token and `soc_enabled`. Without them `mProcessGroups` marks each alert as not sent (`mSkipGroup`: status `local`, reason `soc_not_configured`, shown as «Not sent») instead of queuing it, and `SocSender.mCycle` does the same with what was pending (`mSkipPending`), so the SOC only gets the alerts that come after it is configured and nothing piles up for a SOC that may never exist. The channels work with or without a SOC.
- **Modules come from the repository `localSIEM-modules`, only through the web** ([backend/core/catalog.py](../backend/core/catalog.py)); that repository has no installer. The web offers them in Modules › Installable: only the modules of the repository that are not installed yet. In Modules › Installed it offers **Update** on an installed module when the repository has a newer version (`fCatalog`: `newer` true and the action `update`; with the action `incompatible`, a notice of the localSIEM it needs and no button); it never offers the actions reinstall or downgrade (to reinstall a module: Uninstall and Install). An update is the same call as an installation (`POST /api/admin/module-catalog/{name}` → `fInstall` over the installed copy): the settings and the on/off state are kept (`fFirstInstallation` only runs when there was no previous copy), and `access_changed` (its `read_paths` or `setup_option` differ from those of the replaced copy) tells the web whether root has to run `setup-modules` again. The browser keeps the answer of `GET /api/admin/module-catalog` for 10 minutes (`cCatalogSeconds` and `fFetchCatalog` of `modules.js`), shared by both sections, so that opening Installed does not download the repository every time; «Check the repository» always downloads it again, and installing, updating or uninstalling a module forgets it (`fForgetCatalog`). The archive is unpacked with the `data` filter of `tarfile`; only its folders `mod-<id>` are modules (`fModuleFolders`; the prefix is only of the folder in the repository: the installed folder `<id>/`, the id, the settings, the URLs and the options keep the name without it, and a folder without the prefix is ignored); each module is checked with `fReadManifest` without importing its code and is installed with a rename next to the installed copy. The web runs as `localsiem` and never gives read access to logs nor applies a setup option (they need root): it shows the root command (`fRootCommand`: `manage.py setup-modules` of the same localSIEM). Uninstalling (`fRemove`) moves the installed folder away with a rename and deletes it, also when the module does not load; the settings, the changes of its rules, its events, alerts and read positions stay, and the read access given by root is not taken back. After installing, updating or uninstalling, the web reloads its modules (`mReloadModules`) and the collector restarts (IPC `restart`; systemd or supervise-daemon start it again).
- **Read access to the logs, as root, in one place**: `manage.py setup-modules` (`fGrantReadAccess`: ACLs with a default ACL for the next rotations, and the `adm` group on Debian, for the `read_paths` of the installed modules) is the command the web shows after installing a module, after an update that changes its `read_paths` or its `setup_option` (`access_changed`) and with Reconfigure, and what the installers run at every update (`fGrantLogAccess`, with `--no-restart`).
- **The configuration of the server is never changed** unless root runs `manage.py setup-modules` (or `apply-setup`) with the setup option of a module. `--configure-apache` is applied by the Apache module itself (`mApplySetup`, code in `localSIEM-modules/mod-apache2/setup.py`): one file of its own, `unique_id` enabled, `configtest`, everything undone if it fails, and a reload (never a restart) if it works.
- **Apache specifics live with the Apache module** in `localSIEM-modules/mod-apache2/`: the Apache configuration is parsed directly (so discovery works as `localsiem` without `apache2ctl`), ModSecurity part K is dropped before storing, and the headers and body shown in the request card are rebuilt from the masked raw audit record (`mDisplayRecord`). The core only asks the module of each record (`WebContext.mModule`).
- **Modules switch on and off without restarts**: the web writes `settings.json` and sends `reload` through the socket; the collector republishes its state at once, and the web compares what it saved with what the collector applied (`collector.status.modules`) to show «pending» until both agree.
- **The web reads the `module.json` files when it starts**, and again after installing, updating or uninstalling a module (`mReloadModules`). A module copied or removed by hand needs both services restarted (the web shows it as `not_loaded` until the collector loads it).
- **The requirements of a module are checked only at moments that matter** (collector start and reload, first installation, turning it on, Reconfigure) and kept, because a module may read the configuration of its service to check them. The web never imports the code of the downloaded repository: it checks them on the installed copy.
- **Catching up** (a burst, or what was written while stopped): when a source stops at its read budget the next cycle starts at once; a source more than 5 s (log time) ahead of the slowest source of its module waits for it; and transactions later than what every source behind has read wait (watermark), so the three records of a request are always joined.
- **The logs are only read.** `FileTailer` opens every log with `O_RDONLY`; nothing in localSIEM writes, rotates, truncates, renames, moves or deletes a log of a service (its logrotate file only covers `/opt/localsiem/log/`). The only thing root does on them for localSIEM is read access (`manage.py setup-modules`: the `adm` group and ACLs). Uninstalling leaves the `localsiem_access.log` that `--configure-apache` made Apache write.
- **History is never alerted.** A source without a saved position starts at its end (`Collector.mDiscover`), unless it appeared while this process already followed its module (`sFollowedModules`: a new vhost), which is read from its start when it is up to 5 MB. So neither the first start, nor a module installed or turned on later, nor a file that could not be read until root gave access, nor a restart reads old lines. The position of each file is saved as soon as it is opened, also when nothing new is in it (`FileTailer.vOpenedUnsaved`), so a restart goes on from there. `--from-start` reads the new files from their beginning.
- **Dependencies in a virtual environment** (`/opt/localsiem/venv/`), never `pip --break-system-packages`: pip must not break distribution packages the client's services use (certbot, for example).
- **The web is restricted to the allowed IPs** (and loopback) by the application itself, login included; two-step verification (TOTP, «PYMEHackers localSIEM») is off by default; an administrator turns it on for every account in Settings (`mfa_enabled`), and from then on it is mandatory. The installer only changes it with `--enable-mfa` or `--disable-mfa` (it is not in `install.env`), so an update keeps what was chosen in the web.
- **The SIEM address of the SOC never travels in an alert**: `details` is seen by every analyst of the client; only the query (`details.localsiem.search`) goes.
- **Only the logs of its own server.** There is no remote input: every module reads files of the server localSIEM runs on. `configure.py` stops with «<option> no longer exists: localSIEM has no remote HTTP input, it only reads the logs of its own server.» when given an option of the removed remote input (`lRemovedOptions`: `--enable-http-input`, `--disable-http-input`, `--mode`), and at every run removes what older versions kept for it: `http_input` from `settings.json` (`lRemovedSettings`, `fRemoveSettings`) and three variables from `localsiem.env` (`lRemovedEnvironment`). The installer replaces `backend/` and `frontend/` as a whole, so an update also removes the old files of that input. Events of the module `http` stored by older versions stay in the database until retention removes them.

## 4. Main call paths

**Loading the modules (collector start)**

`Collector.mSetup` → `fCreateModules` → `fListManifests` (`cModulesPath/*/module.json`) → `fReadManifest` (id, entry, settings, `core` ≤ `cVersion`, locales) → `fLoadClass` (`fRegisterPackage` + `localsiem_modules.<name>.<file>`) → `Class(settings, masker, storage, manifest)` → `Module.mStart` → `mCreateCorrelator` → log «Modules: apache2 1.1.0 (on)» → `mCheckRequirements` (`fCheckRequirements` → `Module.mRequirements` of each module → state `<name>.requirements`; log «Module apache2: requirements missing: ...» when they are) → `mLoadRules` → `mDiscover` (enabled modules only) → `mPublishDoctor`. Errors go to `ldModuleErrors` and the loop goes on.

**From a log line to an alert in the SOC**

1. `Collector.mCycle` → `mReadSources` → `FileTailer.mPoll` (new complete lines) → framer of the source (`Module.mCreateFramer`: `LineFramer`, or the audit framer of the Apache module) → `Module.mParse` of the source's module (masking) → `mStoreRecords` → `SqliteStorage.mSaveRecords` (records + FTS + positions, one transaction) → correlator `mAdd`.
2. `mProcessDue` → correlator `mDue` (window passed and watermark reached) → `Module.mBuildEvent` (action taken, scores, detections) → `RulesEngine.mEvaluate` (module rules) → `SqliteStorage.mSaveEvents` → `mDetect` → `Grouper.mAdd` (new group or count +1).
3. `mProcessGroups` (every second) → `SqliteStorage.mGetDueGroups` → `Module.mEnrich` (`mGetIpContext`) → `fSocConfigured` → `fBuildAlert` → `mQueueGroup` (without a SOC: `mSkipGroup`, status `local`).
4. `SocSender.run` (thread) → `mCycle` (without a SOC: `mSkipPending` and nothing else) → `mSendHeartbeat` (every 5 minutes) and `mGetQueueBatch` (≤ 100 alerts, ≤ 1 MiB) → `mDeliver` → `SocClient.mSendAlerts` → `mMarkQueueSent` (SOC codes), or split, set aside, defer with backoff, pause on 507.
5. Besides, `mProcessGroups` → `ChannelSender.mNotify` (`fChannelSettings`, `fSeverityReached`, `fBuildMessage`) → list of each channel on and set up → `ChannelSender.run` (thread, every second) → `mCycle` → `mDeliver` → `TelegramClient.mSendMessage` → state `channels.status` (sent, failed, dropped, last error).

**Setting up Telegram**

`/admin/dashboard/channels/telegram/` → `admin.js fTelegramSection` → «Save and send a test message» → `POST /api/admin/channels/telegram` (`fSaveTelegram`: `cTokenRegex`, `cChatIdRegex`, `fSaveTelegramToken`, `fSaveSettings`, `reload` of the collector) → `POST /api/admin/channels/telegram/test` (`fTestTelegram` → `TelegramClient.mGetMe` → `mSendMessage` with `fTestMessage`) → a notice with the @username of the bot, or with the description of Telegram.

**Turning a module on or off, or saving its settings or rules**

`modules.js fSwitch` (row of Modules › Installed or header of the page of the module; confirmation to turn off; locked, without a request, while `requirements_missing` is not empty) or the forms of `LocalsiemViews.module` → `POST /api/admin/modules/{name}` (`fSaveModule`: `fValidateSettings`; turning on a module that is off: `WebContext.mCheckRequirements` with the settings of the request → 422 `requirements_missing` with the checks not met; `fRules` + `fCleanRules`) → `fSaveSettings` (`modules.<name>` and `rules.<id>` in `settings.json`) → `WebContext.mApplySettings` → `mCollector({"command": "reload"})` → `Collector.mHandleIpc` → `mCycle` → `mReloadSettings` (`Module.mReload`, `mCheckRequirements`, `mLoadRules`, `mDiscover`, `mPublishDoctor`, `mPublishState`). Until `collector.status.modules.<name>.enabled` matches what was saved, `fSummary` answers `pending`.

**Requirements and Reconfigure**

Page of a module (`/admin/dashboard/modules/installed/<name>/`, `LocalsiemViews.module`) → «Reconfigure» (`fReconfigure`, shown when `has_requirements`) → `POST /api/admin/modules/{name}/reconfigure` (`fReconfigure` → `WebContext.mCheckRequirements`: new instance from the installed copy with the saved settings → `fCheckRequirements` → `mRequirements`, kept in `dRequirements` → collector IPC `reload` → `mReloadSettings` → `mCheckRequirements` (state `<name>.requirements`) and, for the modules that are on, `mDiscover` and `mPublishDoctor`) → answer: `requirements`, the `setup_option` of the module and, when they are met, `fRootCommand` → `fShowReconfigured` → `fLoad` (`GET /api/admin/modules/{name}` → `fRequirements`: the newest of the collector's and the web's check) → the switch is unlocked, but the module stays off until the administrator turns it on.

**State of the modules and overview**

`modules.js` (Modules › Installed, and the Modules tab of analysts; every 10 s) → `GET /api/modules` → `fRead` (`collector.status`, `<name>.doctor` and `<name>.requirements` states, `mModuleCounts` of 24 h) → `fSummaries` → `fSummary` per manifest (load errors → `error`; off → `disabled`, with `requirements_missing` when the newest requirement check, `fRequirements`, has errors; collector silent for 2 minutes → `unknown`; not in `collector.status.modules` → `warning`/`not_loaded`; enabled differs → `pending`; doctor errors or unreadable sources → `error`; no sources or missing source → `warning`; doctor warnings are notes and keep `ok`) + `fBrokenSummary` for folders that do not load. `overview.js` (every 15 s) → `GET /api/overview` → `fOverview` → `fRead`, `fSummaries`, `mAlertCounts`, `mQueueStatistics`, `soc.status` and `soc.heartbeat` states, `mHistogram` (hourly buckets of 24 h), `mListGroups` (6 latest).

**The Modules tab, its sections and the page of a module**

`/admin/dashboard/modules/` → `fAdminTab` → 302 to `modules/installed/` (`lModuleSections[0]`) → `fAdminModulesSection` (session first; an analyst → `/user/dashboard/modules/`; `installed` or `installable` → `index.html`; the name of an installed module, the older URL → 301 to `installed/<name>/`; anything else → 404) → `app.js fRoute` (`cPathRegex` accepts a second part; `/admin/dashboard/modules/` and `/admin/dashboard/modules/<name>/` → `modules/installed/` and `modules/installed/<name>/`; a second part under `installable/` or in Users is dropped, and the other tabs take none) → `fShowView("modules", section, item)` → `LocalsiemViews.modules` (`fModuleSections`; Installed: `fLoad` → `GET /api/modules` → `fDraw` → `fCard` per module and, for administrators, `fCheckRepository` once (see «Updating a module»); Installable: `fCatalogPanel`) or, with an item, `LocalsiemViews.module` (its `vParameter` is then the module name). «Configure» of a row (`fCardActions`) → `/admin/dashboard/modules/installed/<name>/` → `fAdminModule` (404 for a module that is not installed) → `LocalsiemViews.module` → `GET /api/admin/modules/{name}`; «Back to the installed modules», Uninstall and a module that is gone (`not_found`) → `/admin/dashboard/modules/installed/`. Analysts: `/user/dashboard/modules/` → `fUserTab` → `LocalsiemViews.modules` with the rows only (the router drops any second part).

**From a query to the results**

`search.js fRun` → `GET /api/search`, `/api/search/histogram`, `/api/search/summaries` → `fParseQuery` (400 with code and position on error) → `fRange` → `SqliteStorage.mSearch` / `mHistogram` / `mSummaries` → `fCompileQuery` → SQLite with a progress handler (time limit, 422 `search_timeout`) → `Accounts.mAudit` → JSON with native display times. A row → `GET /api/events/{id}` → `fEvent` → `mGetEventDetail` → for each record `WebContext.mModule(record.module)` → `mDisplayRecord` (the Apache module adds the headers and body of the audit record) → request card with pivots.

**Direct sign-in with an access token**

`admin.js fTokensSection` → `POST /api/admin/tokens` (`fCreateToken` → `Accounts.mCreateAccessToken`: active analyst, 1–365 days, SHA-256 in `access_tokens`) → the URL `https://<server>:10443/auth/login/auto?token=...` shown once (`fShowSecret`). The analyst opens it → `fLoginWithToken` (`mIsBlocked` with the name `(access token)` → `mCheckAccessToken` → `mRecordAttempt`) → failure: `mRecordLogin` and `/auth/login/?error=<reason>` (`app.js fLoginView` shows it) → success: `mCreateSession(..., "token")` → `mMarkAccessTokenUsed` → `mRecordLogin` → cookie → `next` (a path of this site) or `/user/dashboard/overview/`. Every request → `mLoadSession` (method `token`: analysts only, no second factor, no password change).

**Sign-in and dashboards**

`app.js fLoginView` (the page is only the form: `fAuthLogo`, username, password, the button and, under it, the language and the theme: `fLanguageSelect`, `fThemeToggle`) → `POST /api/auth/login` (`Accounts.mIsBlocked`, `mCheckPassword`, `mRecordAttempt`) → `mfa_enabled` off: session at once (`step` done) → on: `step` totp or enroll (`mStartEnrollment`, QR) → `POST /api/auth/totp` (`mReadChallenge`, `mVerifyTotp`) → `mCreateSession` → `mRecordLogin` (also every failure: `invalid_credentials`, `invalid_code`, `login_blocked`, `challenge_expired`) → cookie `localsiem_session` → `fDone` (`PATCH /api/account` with the language shown when the button was pressed, if the account has another one: the dashboards open in it) → back to `next` (the original URL with its parameters) or to the overview of the role. Every dashboard URL → `fUserTab` / `fAdminTab` (and `fAdminUsersSection`, `fAdminModulesSection`, `fAdminModule` for the sections and the page of a module; no session → `/auth/login/?next=...`; other role → same tab of its own dashboard) → `index.html` → `app.js fRoute` → `fShowView` → `window.LocalsiemViews[tab]` (`LocalsiemViews.module` for `modules/installed/<name>/`).

**Installing or updating the core**

`curl -fsSL -H 'Accept: application/vnd.github.raw+json' https://api.github.com/repos/PYMEHackers/localSIEM/contents/deploy/install-update-reinstall-debian.sh | bash -s -- ACTION options` → `install-update-reinstall-*.sh fMain` (exactly one action, `--install`, `--update`, `--reinstall` or `--uninstall`, or it stops; `fIsInstalled`: `--install` only without localSIEM, `--update` and `--reinstall` only with it; `--reinstall`: `fConfirmRemoval` first; `--configure-*` is refused, pointing to `manage.py setup-modules`, and so is `--modules-from`: modules are installed from the web) → `fEnsurePackages` → `fGetSource` (a complete copy, or `fResolveRef` (the commit of `<ref>`, asked to the GitHub API) and `curl` without cache of `https://github.com/PYMEHackers/localSIEM/archive/<commit>.tar.gz` unpacked in `/tmp/localsiem-install.*`) → `configure.py --check-arguments` → only with `--reinstall`: `fRemoveInstallation` (everything deleted but the downloaded copy) → copy of the core to `/opt/localsiem/webapp/` (files only in working copies, such as `AGENTS.md`, when they exist) → virtual environment → `configure.py` (settings, `modules_repository`, certificates, credentials: `admin` first in `/root/webapp-credentials.txt`, then the system user and the JWT secret if a new one was created; `http_input` and the variables of the remote input of older versions removed) → `fGrantLogAccess` (`manage.py setup-modules --no-restart` → `fGrantReadAccess`: the modules already installed) → services restarted → `manage.py modules` and `doctor` as `localsiem` → where to install the modules (the web).

**Uninstalling a module**

`modules.js fUninstallButton` (row of Modules › Installed, `fCardActions`, or page of the module; confirmation) → `DELETE /api/admin/modules/{name}` (`fUninstallModule` → `fRemove` → `InstallLock` → rename of `/opt/localsiem/modules/<name>` into `.staging-*` → deletion) → `WebContext.mReloadModules` (the module is no longer listed) → collector IPC `restart` (systemd or supervise-daemon start it again → `fCreateModules` without the module) → `fForgetCatalog` → the list is drawn again, or the page of the module goes to `/admin/dashboard/modules/installed/`. `settings.json` keeps `modules.<name>` and `rules.<id>`.

**Installing a module from the web**

`/admin/dashboard/modules/installable/` → `modules.js fCatalogPanel` → «Check the repository» (`fCheck` → `fFetchCatalog(true)`) → `GET /api/admin/module-catalog` (`fGetCatalog` → `fFetchCatalog` → `fResolveRef` → `fArchiveUrl` → `fDownload` in `/opt/localsiem/run/catalog.*` → `fCatalog` → `fModuleFolders` (folders `mod-<id>`) and `fListManifests`) → only the items with `installed` null are listed (`fDraw`; `catalog.all_installed` when every module of the repository is installed, `catalog.empty` when it has none) → «Install» (`fInstall`) → `POST /api/admin/module-catalog/{name}` (`fInstallFromCatalog` → `fFetchAndInstall` → `InstallLock` → `fResolveRef` → `fDownload` → `fInstall`: `mod-<name>` → `/opt/localsiem/modules/<name>`) → `WebContext.mReloadModules` → first installation only: `fFirstInstallation` (`WebContext.mCheckRequirements` on the installed copy → if a requirement is missing and `modules.<name>.enabled` was never saved, `fSaveSettings` with `enabled: false`) → collector IPC `restart` (`Collector.mHandleIpc` → `vStop`; systemd or supervise-daemon start it again → `fCreateModules` loads the module → `mCheckRequirements`) → answer with `requirements_missing` and `fRootCommand` → `fForgetCatalog` → the module leaves the list (`fDraw`) and a dialog opens (`P.fModal`, «<module> installed», `fResult`): what the server lacks (and Reconfigure), or the command for root (and the hint of its `setup_option`); Close, or «See the installed modules» → `/admin/dashboard/modules/installed/` → the administrator runs it as root (`manage.py setup-modules [--configure-apache]` → `fApplySetup`, `fGrantReadAccess`, `fRestartServices`, `fDoctorAsLocalsiem`).

**Updating a module**

`/admin/dashboard/modules/installed/` → `LocalsiemViews.modules` (administrators) → `fLoad` (`GET /api/modules` → `dLast` → `fDraw`) and, once, `fCheckRepository` (`modules.checking_updates`) → `fFetchCatalog(false)` (the answer kept if it is less than 10 minutes old, `cCatalogSeconds`; otherwise `GET /api/admin/module-catalog` → `fGetCatalog` → `catalog.py fFetchCatalog` → `fCatalog`: `newer` and `action` of each module) → `dNewer` (the items with `newer` and the action `update` or `incompatible`) → `fDraw` → `fCard` → `fUpdateNotice` (only while the `installed` of the item is the version of the row: `modules.update_notice` and «Update», or `modules.update_incompatible` without a button) → «Update» → `fUpdate` (`P.fConfirm`, «Update the module»; `sUpdating`: «Updating…», also across the 10-second refreshes) → `POST /api/admin/module-catalog/{name}` (`fInstallFromCatalog` → `fFetchAndInstall` → `InstallLock` → `fResolveRef` → `fDownload` → `fInstall`: the new copy swapped for the installed one, with `previous` and `access_changed`) → `WebContext.mReloadModules` → no `fFirstInstallation` (`previous` is not `None`: the settings and the on/off state stay as they were) → collector IPC `restart` → answer → the module leaves `dNewer` → `fForgetCatalog` → toast `modules.updated_toast` → only with `access_changed` or without `collector_restarted`: a dialog (`P.fModal`, «<module> updated», `fUpdateResult`: the command for root, `fRootCommand`, with the hint of its `setup_option`; or restart the `localsiem` service) → `fLoad`. If the check fails, `vRepositoryNote` shows `modules.updates_failed` and the list works as usual. The web never reinstalls a module nor installs an older version (actions `reinstall` and `downgrade`).

## 7. Extension points

### How to add a module (SSH, Postfix, MariaDB...)

The core does not change: no registration in the collector and no defaults in `config.dDefaults`.

1. Create the folder `localSIEM-modules/mod-<name>/` (the name: `[a-z][a-z0-9_]{1,31}`; the prefix `mod-` only goes in the folder of the repository: the `id`, `vName`, the settings, the URLs, the options and the installed folder `/opt/localsiem/modules/<name>/` use `<name>`) with a `module.json` (`id`, `version`, `core`, `entry`, `default_enabled`, `read_paths`, `setup_option`, `settings`; see [Core and modules](#architecture) and the header of [backend/core/registry.py](../backend/core/registry.py)).
2. Write the subclass of `Module` named in `entry` ([backend/core/module.py](../backend/core/module.py)): `vName` equal to the id (`<name>`), `mDiscover` (sources with stable `key`s; read your settings with `mModuleSettings()`), `mCreateFramer` (usually `LineFramer`), `mParse` (record with time, correlation, parse_status, fields and masked raw), `mCreateCorrelator` (an object with `mAdd`, `mDue(pNow, pForce, pWatermark)` and `mPendingCount`), `mBuildEvent` (event dict with `action` and `detections`) and optionally `mStart`, `mRulesPath`, `mRuleFunctions`, `mEnrich`, `mDoctor`, `mRequirements`, `mHealth`, `mSkipped`, `mSetLowDisk`, `mDisplayRecord`, `mSetupSnippet` and `mApplySetup`. Import the module's own files relatively (`from .parsers import ...`) and the core as `backend.core.*`; do not add `__init__.py`.
3. Add `locales/en-GB.json`, `en-US.json`, `es-AR.json` and `es-ES.json`: `name`, `summary`, `settings.<key>.label` / `help` (and `fields`, `add`, `remove`, `empty` for `records`) and `choices`.
4. Put its YAML rules in `mod-<name>/rules/` and return that folder from `mRulesPath`.
5. Decide what «action taken» means for the service (for example, an IP banned by fail2ban) and set `action` accordingly: only events without an action taken produce detections.
6. If the module needs software on the server (the service it watches), return it from `mRequirements` as checks like the ones of `mDoctor` (with the command that installs it in `fix`), without using the storage and without installing anything: without it the module is installed turned off and cannot be turned on until Reconfigure finds it.
7. Declare in `read_paths` the folders of its logs, so `manage.py setup-modules` (the command for root the web shows, also run by the installer at every update) gives `localsiem` read access. Its `setup_option` (any `--configure-...`) is accepted by `manage.py setup-modules` and applied as root → `mApplySetup`.
8. Publish it in the repository `localSIEM-modules` (folder `mod-<name>/`): it appears in Modules › Installable while it is not installed, the only way to install it (in a development copy you can copy the folder to `/opt/localsiem/modules/<name>/` and restart `localsiem` and `localsiem-web`). To publish a new version, raise `version` in its `module.json`: Modules › Installed offers it with Update (if it also raises `core` above the installed localSIEM, it only says which localSIEM it needs); if the new version changes `read_paths` or `setup_option`, the web shows the command for root again after the update.

### How to add a setting to a module

Add it to `settings` of its `module.json` (type and default) and its label and help to its locale files; read it with `mModuleSettings()`. The web builds the field, `fValidateSettings` checks it and the collector applies it at once on the next reload.

### How to add a rule

Create a YAML file in the `rules/` folder of the module (see the header of [backend/core/rules.py](../backend/core/rules.py) for every key and operator). Example:

```yaml
id: apache-xmlrpc-burst
name: "Apache: burst of XML-RPC calls"
category: bruteforce
type: authentication
severity: medium
kind: threshold
when:
  method: POST
  path: /xmlrpc.php
  action: none
by: [ip, vhost]
window: 60
threshold: 30
description: "{count} POST requests from {ip} to /xmlrpc.php of {vhost} in {window} seconds."
search: "ip:{ip:q} path:/xmlrpc.php"
```

The collector loads it on its next start or settings reload; it then appears in the rules table of the page of its module (Administration › Modules › Installed › Configure), where it can be turned off and its severity, threshold and window tuned (overrides in `settings.json` under `rules.<id>`). `enabled: false` in the file turns it off by default. Conditions needing code use `{function: name}` with a function returned by `mRuleFunctions` of the module.

### How to add a search field

Add it to `dFields` in [backend/core/query.py](../backend/core/query.py) and to `dTextColumns` / `dNumberColumns` (or a special case) in `fCompileField` of [backend/core/storage_sqlite.py](../backend/core/storage_sqlite.py); a new column also needs the schema, `lEventColumns` and an index. Document it in the help (`help.fields` of the four locale files) and in the manuals.

### How to add an API endpoint or a dashboard tab

Endpoints go under `/api/` in the `fRegister*` function of their area (Swagger documents them). A tab needs its route in `lUserTabs` and/or `lAdminTabs` ([backend/web/app.py](../backend/web/app.py)), an entry in `ldTabs` ([frontend/assets/app.js](../frontend/assets/app.js); `group`, `adminGroup`, `adminOnly`), a view in `window.LocalsiemViews` (a new script must be added to `frontend/index.html`) and its texts (`nav.<tab>` and the view's keys) in the four locale files. A tab with sections, like Users and Modules, also needs its list of sections in `app.py` and in `app.js` (`lUserSections`, `lChannelSections`, `lModuleSections`), the redirect of the tab to its first section in `fAdminTab`, a route for its sections (`fAdminUsersSection`, `fAdminChannelsSection`, `fAdminModulesSection`), its case in `fRoute` and the sub-tabs in its view (`fUserSections`, `fChannelSections`, `fModuleSections`).

### How to add a channel (e-mail, Slack...)

In [backend/core/channels.py](../backend/core/channels.py): its name in `lChannels`, its block in `dDefaults["channels"]` ([backend/core/config.py](../backend/core/config.py); a secret goes to a file of its own in `config/`, mode 600, never to `settings.json`), and its case in `fChannelSettings`, `ChannelSender.mConfigured` and `ChannelSender.mDeliver` (a client like `TelegramClient`, whose errors never carry the secret). Then its API in `api_admin.py` (like `fSaveTelegram` and `fTestTelegram`), its section in `lChannelSections` of `app.py`, `app.js` and `admin.js` with its view (like `fTelegramSection`), the texts `channels.section_<name>` and the ones of its view in the four locale files, and its part of the manual. The General section lists it by itself (`channels` of `GET /api/admin/channels`).

## 8. Measured resource usage

Measured on a Debian 13 server (mod_security2 2.9.11, CRS 3.3.7) with the Apache module, with the systemd limits of the units (`MemoryMax` 300M / 200M, `CPUQuota` 50 %, `Nice` 10, idle I/O):

| Situation | Collector (RSS) | Web (RSS) | Total |
|---|---|---|---|
| Idle, after start | ≈ 28 MB | ≈ 26–55 MB | ≈ 55–80 MB |
| Burst of 30 000 requests in about 60 s, **every one** with an audit record (≈ 1.8 GB of audit log because of part K) | peak ≈ 160 MB | ≈ 40 MB | peak ≈ 200 MB |
| After the burst | ≈ 70 MB | ≈ 26–40 MB | ≈ 100 MB |

During that burst the collector caught up about 40 s after the last request, stored exactly one event per request (30 000 of 30 000, all with their three sources) and sent three alert groups instead of thousands. Alpine 3.24 at rest: collector ≈ 26 MB, web ≈ 54 MB.

Disk: about 0.8 KB per request without matches (access line, event, index) and about 10–13 KB per request with an audit record and several ModSecurity lines in error.log. A typical PYME site with tens of thousands of requests a day and a few per cent of them audited stays well inside the default maximum (lesser of 15 % of the disk and 10 GB) for the 90 days of retention; when the maximum is reached the oldest events go first.
